The key comes first, once

Backups are encrypted, and the first one will not run until the key has been copied somewhere sloop cannot reach. This is not a nag that can be dismissed and forgotten — it is a refusal, and with no terminal to ask at it exits 2:

sloop key export once, and every run after it goes through. The backup key is the page for what that key is and what losing it costs; everything below assumes it has been done.

Taking one

Two timestamps, both deliberate. The directory is named in UTC so backups sort correctly and survive a daylight-saving change; every line a human reads is in local time. The sha256 is over the dump as written, and backups list --check compares it again later.

Every database, and the one that fails

--all is the one you schedule, and its rule is the important one: it never stops on a failure. One unreachable database in a set of thirty must not cost you the other twenty-nine.

The run worked to the end, backed up the three that answered, and named the one that did not. The last line is the one to read in a log — zero, one or several, always counted and always named. The exit code is the failure's own: 3 here, because what went wrong was a connection.

A directory per run, or one kept current

--sequential is the default and is what you saw above: a directory per run, named for the moment it was taken, kept until retention removes it.

--replace keeps exactly one, at a fixed path ending in latest. For a database you want a current copy of rather than a history — and the path never changes, so something else can pick it up without being told where to look.

Retention

backups prune deletes what is past a limit, after showing you which. Two limits, and they can be combined: --keep <N> for the newest N, and --older-than <AGE> for 12h, 30d, 6w.

--dry-run is a real rehearsal: it does every bit of reading and deciding and stops where it would delete. The list it prints is the list the real run removes.

A --replace copy is skipped by retention and says so. There is one of it, at a fixed path, and deleting it on age would leave a database with no current copy at all — which is the opposite of what a retention rule is for. --include-broken widens the sweep to unfinished and damaged directories, which are otherwise left alone so that a failure is still there to look at.

Putting one back

With no --from it takes the newest. Everything after loaded in is the part that makes this a restore rather than a file copy: it reads the per-table counts out of the manifest and counts the database it has just written, table by table, and only then says the two matched.

--from takes the directory's own name — the UTC stamp, exactly as backups list shows it. A name that is not there is an error before anything is touched, not halfway through.

Verification is exact, not estimated

Every table is counted on both sides with count(*) — one query_to_xml statement against one snapshot for PostgreSQL, one UNION ALL for the MySQL family. Not a sample, not the catalogue's opinion.

Why an estimate is not proof

n_live_tup is a planner statistic, and it has been observed reporting double the true count on a table this project was looking at. It also reports zero for every table of a freshly restored database until something analyses it — so a verification built on estimates would call a perfect restore a catastrophe.

The estimate is still available, for a table too large to count on every run. SLOOP_VERIFY=fast asks for it, and sloop labels it wherever it appears:

a glance and not a proof is sloop's own wording, printed every time. And under fast mode a count can never fail a run on its own — only a table that is genuinely not there, which is a fact from the catalogue rather than from a statistic.

Drift is not loss

A source that is still being written to gains and loses rows while a dump is being taken, so two sides differing by a few rows is the normal state of a live database, not a fault. sloop says so in those words rather than calling it an error.

What is not normal, and what does fail: a table that arrived empty when the source had rows, or a table that did not arrive at all. Those are the two things a dump silently losing data looks like, and both are failures.

Exit 0 against exit 6

Both mean the work completed. Only one of them means the work was proved, and automation that treats them the same is automation that will one day keep a backup nobody can restore.
