Most databases worth backing up are not listening on the public internet. sloop reaches one through an SSH server you can already log into: it opens a forward, binds a local port, and hands that port to pg_dump or mysqldump, which never learn that SSH was involved.

Registering one

The SSH settings live on the record, beside the connection, so you give them once and every command after that just takes the name:

--host is what the SSH server sees, not what you see

This is the one thing that catches people, so sloop says it at registration time. --host 127.0.0.1 above means localhost as the bastion sees it — the database running on the bastion itself. A database on a third machine would be its address on the bastion's network. And --ssh-port is the SSH server's port, never the database's.

--ssh-user falls back to ~/.ssh/config and then to your own username. --ssh-port is 22 when left out. --ssh-identity takes a particular private key exactly as ssh -i does — and when you leave it out, the agent and ~/.ssh/config decide, which is the documented default. sloop never reads your key file and never copies it.

Where the key's passphrase comes from

The same four routes a database password takes, with the same flags wearing an --ssh- prefix: --ssh-keyring, --ssh-encrypted-file, --ssh-env <VARIABLE> and --ssh-passphrase-from <COMMAND>, plus --ssh-passphrase-stdin for storing one with no terminal.

A registry holds the route and never the passphrase, which is exactly the rule database passwords follow. And the note is the point rather than a problem: a command that is not installed yet is fine at registration time, because it is run when it is needed rather than now.

--no-ssh takes the forward off and the connection becomes a direct one.

One forward per session, not per command

sloop opens one long-lived forward per remote server — the first time something needs it — and closes it when sloop exits. Ten operations against one server in one menu session authenticate once. A tool that made you touch a hardware key before every single command would be a tool people stop using.

Why sloop runs your ssh rather than embedding one

This is a deliberate decision and it is the same one sloop makes about curl. Four reasons, and the first is the product:

    @for (reason of reasons; track reason.title; let i = $index) {
  1. {{ i + 1 }}

    {{ reason.title }}

    {{ reason.detail }}

    2. }

Your credentials never leave your machine, and this is where that claim would have been quietly broken. An embedded SSH client can open a socket to anywhere. So the build refuses one — the same check that denies reqwest and hyper denies ssh2, russh, thrussh and the rest, across normal, build and dev dependencies, on every target.

A claim that holds only because the check is narrow is not worth making. That is why the check is not narrow — and why the honest way to reach a closed-off database is to run the ssh you already trust.

When it fails, it fails in OpenSSH's words

Which is the best evidence there is for everything above. Here the bastion does not exist:

ssh: Could not resolve hostname … is not sloop's sentence. It is the message your own OpenSSH printed, handed straight back to you — so a wrong key, a rejected host, an expired certificate or a ProxyJump that failed all arrive as the message you would have seen typing ssh yourself, and you fix them the way you already know how.

Every --ssh- flag is on the command reference, generated from --help.
