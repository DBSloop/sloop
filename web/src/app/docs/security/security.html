Your credentials never leave your machine. No telemetry, no analytics, no update pings. cargo tree on this repository shows no HTTP client in the dependency graph — there is nothing in the binary that could phone home.

That is a claim about a dependency graph, which makes it a claim anybody can check. So the first section is how, and it takes about thirty seconds.

An embedded SSH client can open a socket to anywhere, so the promise above would stop being true while a check that only looked for HTTP clients still passed. A claim that holds only because the check is narrow is not worth making — which is why sloop runs your own ssh instead.

A registry holds a route, never a value

There is no spelling of a password a registry will accept. It stores which of four routes to take, and the value is fetched at the moment it is needed — which is what makes it impossible to put a password there by accident.

@for (route of routes; track route.flag) {
{{ route.flag }}
{{ route.where }}
{{ route.when }}
}

sloop db list shows the route beside every database and cannot show a password, because there is not one there to show. Databases and registries has that listing.

Nothing in argv, so nothing in ps

A password reaches a child process through a pipe, or through that one child's environment — never as a command-line argument. Anybody running ps on a shared machine while a backup is going sees the command and not the credential.

Which leaves one hole sloop cannot close: a password you typed into a URL was already in your shell's history and in ps before sloop ever ran. It says so rather than quietly accepting it, and then keeps its own half of the bargain:

A log you could paste into a public issue

--log-file writes what the run printed, without colour and with anything that reads like a credential removed. That holds for two reasons, and only one of them is a filter.

The structural half: the one line that carries a real password goes through a function that has no logging in it at all. sloop does not redact its own passwords out of its logs — it never writes them.

The net under it is for credentials that arrive inside something else: a URL with a password in it, a key=value pair whose key says what it is, or a word after something that announces a secret. Like a token inside a --password-command you wrote, which sloop cannot see coming:

A redactor is a net, not a design

Note the terminal above shows the token in full — it is the command you typed, and hiding it from you would be theatre. It is the log that is scrubbed, because the log is the thing that ends up in an issue. And what keeps sloop's own passwords out of logs is not this filter; it is that they are never printed.

Config is parsed, never evaluated

Real passwords contain $, backticks, >, #, quotes, pipes, backslashes and spaces. Nothing sloop reads is ever sourced or eval'd, so none of that is interpreted. Here is a PostgreSQL role whose password is nothing but metacharacters:

Registered through a pipe, stored in the keyring, and read back on a later run to open a real connection. $HOME did not expand, the backticks did not execute, the > did not redirect and the # did not start a comment.

A \r is the one character sloop removes — Windows editors add them, and the authentication failure that follows is invisible.

What this is not

None of it is a substitute for the database's own access control. sloop runs as you, with the credentials you gave it, and can do exactly what those credentials allow — the privileges a backup role needs is the page for keeping that set small. And an encrypted backup is only as safe as the key: lose it and the backups are unreadable, leave it beside them and they are not protected.

Securing the machine and the network is still the operator's job. What sloop guarantees is narrower and checkable: it cannot send your credentials anywhere, because it cannot send anything anywhere.
