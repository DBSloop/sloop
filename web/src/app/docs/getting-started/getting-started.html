You need two things: sloop installed — the one-liner takes a few seconds — and a PostgreSQL, MySQL or MariaDB database it can reach, with a user, a password and a port. Nothing else has to be set up in advance.

The example below uses a PostgreSQL database called shop with two tables and 10,601 rows in it. Substitute your own connection string and every command is the same.

It is safe to run again. On a machine that is already set up it reports what it found rather than changing anything, and brings the schema forward if a newer sloop needs a newer one — so it is the right thing to reach for when you are not sure, and after an upgrade.

2 · Register your first database

Tell sloop about a database once and you refer to it by name from then on. The name is yours — the label you will type — and it does not have to match what the database is called on the server.

It asks for the password and does not echo it, then stores it in {{ keyring() }}. The registry holds a route to the password, never the password. There is no spelling of a secret that a registry will accept, which is what makes it impossible to put one there by accident.

If that is not what you want, --encrypted-file keeps it in an Argon2id-encrypted file, --env ORDERS_PW reads it from an environment variable at run time, and --password-from "op read op://vault/db/pw" runs a command and takes it from the output. The password never appears in argv, so it never appears in a process listing.

3 · Export the backup key

This is a step, not an aside, and the next command will refuse without it. Backups are encrypted with an age keypair, and the asymmetry is the point: the public key sits in the registry so a scheduled backup needs no secret to unlock, and the private key lives in {{ keyring() }} so only a restore ever reads one.

That last line is the whole of it. Put it in a password manager, or on paper in a drawer — somewhere sloop itself cannot reach, because a backup and the key to it sitting on the same disk is one disk failure away from being neither.

What losing it costs

Lose the machine and you still have the backups, as long as you have this line — sloop key import puts it on the new one. Lose this line and every encrypted backup that registry ever took is unreadable, by you and by anybody. Nothing can replace it, which is why sloop refuses to take the first encrypted backup until it has been exported or you have explicitly declined.

4 · Take the first backup

One command, and it does not report success until it has counted what arrived.

Two timestamps, and both are deliberate: the directory is named in UTC so backups sort correctly and survive a daylight-saving change, and every display is in local time so a human reads the one they think in. The sha256 is over the dump as written, and backups list --check compares it again later.

5 · See what you have

Newest first, sizes totalled, and every time in local time. --check re-reads every byte of every dump and hashes it against what the manifest recorded — which is a thing you ask for rather than something a listing does on the way past.

6 · Put it back

A backup nobody has restored is a hope, not a backup. Do this once now, against something you do not mind replacing, so that the first time you run it is not the day you need it.

The name is typed, never clicked. A y is one keystroke away from a mistake, and this command replaces what is in a database; typing the name out means the thing being destroyed has been read. With no terminal to ask at it does not prompt at all — it exits 2 and names --confirm shop, which has to match exactly, so a scheduled line names what it replaces and cannot be repointed at something else by editing one flag.

And it verifies. Not an estimate: count(*) on both sides, per table, compared with what the manifest recorded. If the numbers disagree the run exits 6 — which is neither success nor a crash, and is the exit code worth wiring an alert to.

Where to go next

That is the whole loop. Three things are usually next:

  • Stop doing it by hand. The background service registers sloop with your machine and takes the backup on a schedule with nobody logged in.
  • Check the role before you trust the dumps. sloop doctor reports what each registered role may actually do. On MySQL and MariaDB, one missing grant produces a dump with every trigger and stored routine silently absent from it, and an exit code of 0.
  • Copy a database instead of backing it up. mirror and sync move one database into another — exactly, or merged. They are different commands and the difference matters.
