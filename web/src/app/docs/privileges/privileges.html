A backup that looks fine, exits 0, has a plausible size and a valid checksum — and has lost every function, every procedure and every trigger in the database. You would find out at the restore, which is the worst possible moment to find out anything.

sloop doctor asks, so you do not find out later

Rather than discovering this during a backup, doctor asks each registered connection what its role can really do — and prints the exact GRANT for anything missing:

Exit 8 exists for this. A health check that exits 0 while a role is quietly writing incomplete dumps is worse than no health check, so doctor has a code of its own and automation can act on it.

Run the lines it printed — and only those — and it changes its mind:

It asks three questions, not one: can this role back the database up, can it restore into it, and can it delete it from the server. A role that dumps a database perfectly may be unable to restore one, and a role that can do both may still be refused at db drop — so they are reported apart, because they are needed at different times.

The third one has exactly one answer per database. PostgreSQL has no GRANT DROP: a role may drop a database when it owns it, and one role owns it. That is why weak above is still short of that one line after everything else was granted — and why the run exits 0 anyway. Only the first question reaches the exit code, because a role that takes complete backups is a healthy role; the other two are reported so that nothing is discovered at the moment it matters.

In practice

Make the role, run sloop doctor, paste what it prints. That is the whole workflow — and sloop db create skips it entirely by making the database and a role that already has what it needs.

doctor also checks the client tools and sloop's own PostgreSQL; the command reference has its flags.
