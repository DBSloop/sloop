Two commands, and the second is the first plus the binary. They share one implementation, so they can never drift into destroying different things.

Backups are never deleted. Not by reset, not by uninstall, not ever. A registry is a minute of typing and a PostgreSQL is a download; a dump that is gone is gone.

One question decides how much goes

Who installed the PostgreSQL. sloop wrote the answer down at setup — origin in server.toml — and reset reads it rather than guessing.

origin = sloop

sloop downloaded it and installed it under ~/.sloop, so it is sloop's to take away. The cluster and its binaries go, in one directory. sloop setup downloads and installs again.

origin = machine

The PostgreSQL was already here and sloop was a guest on it. Two statements run — DROP DATABASE and DROP ROLE — and both name something sloop created. Not the server, not another database, not another role.

The one thing that can still be lost

Backups survive reset. Being able to read them may not, and this is the whole reason the page exists.

An encrypted backup is readable only with its private key. On a machine with a working keyring that key lives in the keyring, which reset does not touch. But on a machine with no keyring — a headless Linux box — the key lives in the Argon2id vault, and the vault is inside sloop_database, which is precisely what reset destroys.

Run this before you run reset

sloop key export — and keep the line it prints somewhere sloop cannot reach. Without it, every encrypted backup this machine took becomes a file nobody can open. There is no recovery, no reset and nobody to ask.

Reset says so itself, in the block above, before the name is typed rather than after. It is the only warning on this page that describes something irreversible that reset does not do — it describes what you will have done by running it unprepared.

uninstall is reset plus the binary

Everything above, and then sloop itself: the directory the installer made and the PATH entry that points at it.

The open shell is the one thing it cannot fix. A shell read its environment when it started and keeps it; sloop will still resolve in the window you ran this in until you open a new one. It says so rather than leaving you to notice.

Coming back

sloop setup, and the machine is ready again. What it cannot restore is what was in the database it destroyed: the registry, the schedules and the service's history are gone, and the databases they described have to be registered again.

The backups are still on disk with their manifests, so restoring one needs the database registered again and — if it was encrypted — the key you exported.
